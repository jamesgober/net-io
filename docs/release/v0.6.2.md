# net-io v0.6.2 - Patch

**Fixes for Windows (a deadlock, a backlog cut to 200, and closes held open after a reset), the reactor's short connections spread over its workers again, and drains that no longer cut a request short on Linux.** No API change; every 0.6 program builds unchanged.

## What is net-io?

The network IO substrate for the `-io` and `-net` crates: listeners and sockets, the life of each connection, the limits and timeouts around it, graceful drain and restarts, and the seams a connection gate and a TLS engine plug into. It is protocol-free and has no runtime dependencies.

## Fixed

**Upgrade if you run net-io on Windows.** A process whose threads ended after using a `TcpConnection` could freeze entirely: every thread start and every thread exit waited for ever. Each such thread kept a small wake socket, and Windows runs the code that closed it at thread exit under the loader lock, where a socket call can deadlock against another thread loading a Winsock extension (the reactor's IOCP driver and file sends do). A thread's wake socket is now kept for the next thread instead of being closed there. It affected 0.3.0 to 0.6.1 on Windows, and showed up as net-io's own tests hanging in about 1 run in 14.

**Windows cut every backlog past 200 to 200.** Windows takes a plain `listen` backlog as at most 200 pending connections, so net-io's default of 1,024 was really 200. On a busy host, when the accept thread fell behind, connections past the 200th got no answer and their clients waited about 21 seconds to fail. net-io now asks for a larger backlog in the form Windows honours (`SOMAXCONN_HINT`, up to 65,535), and `ListenerInfo::backlog` reports the real value.

**Windows held a closing connection open after the peer reset it.** When a client reset the connection after reading its reply (a TLS client that does not read `close_notify` does this), the Windows reactor kept the closing connection until the 2-second linger ran out, with its buffers and its place under the connection cap. Under many short connections they piled up. A reset now ends the close at once.

**A drain could cut a request short on Linux.** On the blocking pool, a drain that found a connection waiting with its next request already queued shut the connection's read side. The queued bytes still arrived, but the rest of that request read as end of stream, so a handler mid-exchange was closed. A drain now leaves such a connection to answer first, and closes it once it is idle again.

**The reactor used one worker for short connections.** When every worker had no open connections, which is the usual state under a load of short connections (a TLS handshake and one request each), the reactor always picked the first worker, so one core did all the work while the others idled. tls-net measured about half the handshake throughput it should have had. Ties now go round the workers.
