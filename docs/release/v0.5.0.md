# net-io v0.5.0 - Feature complete

**The reactor, on every platform, and Windows as a full peer of Unix.** v0.5.0 adds net-io's own event loop on epoll, kqueue, and I/O completion ports beside the blocking pool, Windows named pipes and AF_UNIX, the Windows hand-off, Happy Eyeballs, and FreeBSD.

## What is net-io?

The network IO substrate for the `-io` and `-net` crates: listeners and sockets, the life of each connection, the limits and timeouts around it, graceful drain and restarts, and the seams a connection gate and a TLS engine plug into. It is protocol-free and has no runtime dependencies; the few OS calls `std` does not expose go through the crate's own small, tested FFI layer.

## What's in 0.5.0

- **The reactor.** One event loop per CPU, on epoll, kqueue, or an I/O completion port. Sessions need no change: the same `Session` runs on either driver, with the same limits, deadlines, PROXY, TLS, drain, kill, and `Completer`. `DriverKind::Auto` picks it; a blocking handler stays on the pool.
- **10,000 idle connections, no buffers.** An idle connection holds its state and nothing else: 17 MB of heap for 10,000 on Linux, 18 MB on Windows, tested on every OS in CI. On Windows an idle connection waits with a zero-byte receive, so it pins no memory in the kernel either.
- **Back-pressure that does not drop anyone.** With the buffer budget spent, a connection's reads pause and TCP pushes back on its peer. They resume, oldest first, as buffers free.
- **Windows named pipes.** Owner-only by default, remote clients always rejected, and a name another process took first is an error, not a shared pipe. A pipe has the limits, deadlines, kill handle, and gate of a socket, on both drivers.
- **AF_UNIX on Windows,** on both drivers.
- **The Windows hand-off.** Hand listening sockets to a new process over a pipe: under about 1,000 connections per second between two processes, nothing is refused. Windows lets a socket description be used twice; a nonce makes it once.
- **The public `Driver` interface.** `new_reactor_driver` gives you the completion-shaped driver directly: operations own their buffers until the completion hands them back, and a cancel always ends in exactly one completion. Tier 3, unstable until 1.0.
- **Happy Eyeballs** on `connect_host`, and **FreeBSD**, tested in a VM in CI.

## Security

Cancelled IO cannot touch freed memory on Windows: an operation and its buffers live in a block the kernel owns until its packet is dequeued, so nothing can reuse a buffer a cancelled receive may still fill (T-18). A listener never joins a completion port, so one handed to another process stays usable there (D-016), and the driver refuses one. Every suite passes under AddressSanitizer and ThreadSanitizer on Linux, in CI on every change.

## Performance

`docs/PERFORMANCE.md` has the numbers. On Windows the reactor beats the blocking pool: 1.11x at 64 connections, 1.63x at 256, and about twice the blocking round-trip rate on one connection. On Linux one connection costs a round trip of 8.5 us against 7.8 us on the pool, one more system call. Throughput with many connections on Linux is below the pool on the only machine these were measured on, a WSL2 guest shared with other builds, and meeting it is the first item of `0.6.0` (register R-20). A timer takes 26 to 30 ns to insert, 4 to 5 ns to extend, and 5 to 6 ns to cancel; the insert misses its 20 ns target.

## Platform notes

An idle reactor connection's state is 848 bytes, against an early estimate of 512 (register R-18). The std-only fallback for other targets moved to `0.6.0`; those targets stop at a compile error that says so. Details for every platform are in `docs/PLATFORM-NOTES.md`.
